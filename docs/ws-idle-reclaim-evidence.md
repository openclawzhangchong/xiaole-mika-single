# 证据：云端按「业务消息空闲」回收 WS（1005 / ~60–70s）与 pingInterval 无效

> 入库证据说明。原始日志均来自真机（realme RMX3161，`7f:f1:b7:5e:ef:aa`，M5Stack CoreS3 身份），
> 日志文件：`<TEMP>\xiaole-apk\A_3min.log`（下称 A 日志）。

> **81 起口径变更（2026-11-06）**：ColorOS 息屏会冻结进程与 Dart isolate，45s 保活只能在**前台**生效。
> 后台/息屏不再要求 tick、不再发 `listen{stop}`；亮屏 ≤3s 自动恢复。本文的“生产默认保活（45s）”仅描述**前台**行为，不再承诺“锁屏不断线”。

> **82 修正（2026-11-06）**：81 的“后台失败 3 次停手”仍会形成风暴——服务端每 62s 空闲回收，
> 客户端重连成功即把退避计数清零，于是“重连→62s 被掐→再重连”无限循环（1006 间隔精确 62 秒）。
> 82 改为**后台一次都不重连**，并在进入后台时主动关闭连接（不等服务端 62s 回收，避免留下 1006）：
> `paused`/`hidden` 后不排重试、不建退避定时器，只记
> `[KEEPALIVE] 后台断开，等待亮屏（82 口径）`；回前台立即补连 1 次，仅这一轮允许 2s/5s/15s 共 3 次。

## 1. 结论（可入库一句话）

**服务端对 WebSocket 的回收依据是"业务消息空闲"，不是 TCP/WS 层的 ping。**
6.11.6 已把 WS 层 `pingInterval` 设为 25s，真机仍每 **70s 左右**被 `code=1005` 静默关闭；
未加 ping 的 6.11.5 则是 **60.26s** 被 `code=1006` 回收——两者同量级，说明 ping 没有续命作用。
上游文档（`websocket_zh.md` / `mcp-protocol_zh.md`）没有定义任何 WS 心跳或空闲超时条款，
所以只能靠实验确认"哪条业务消息算活跃"（见 §4）。

## 4. 心跳实验设计（v6.11.8，默认关）

实现位置：`lib/core/network/xiaozhi_websocket_manager.dart`（`WsProbeMode` + `[PROBE]` 日志）；
开关入口：开发者中心「调试 → WS 保活」（`AppFeats.wsKeepaliveMode`，v6.11.11 起默认 `auto`，间隔 45s，可 10–120s）。

| 候选 | 定时消息 | 目的 |
|---|---|---|
| ① `hello` | 完整 hello（version/device-id/features/audio_params） | 重握手是否算活跃 |
| ② `detect` | `{"type":"listen","state":"detect"}` | 文档里的唤醒态是否算活跃 |
| ③ `abort` | `{"type":"abort","reason":"heartbeat"}` | 控制类消息是否算活跃 |
| ④ `ping` | 不发业务消息（仅 WS `pingInterval=25s`） | 对照组，应仍在 ~70s 被 1005 |

记录点（全部走 `[PROBE]` 前缀，真机用 `adb -s 36c77fb6 logcat | findstr PROBE` 抓）：
启动候选与间隔、每次 tick 的 `seq/t/recv`、本连接首个服务器帧时刻、断开时 `存活秒数 + 发送数 + 收到帧数 + closeCode`。

**判定阈值**：同一手机、同一智能体、安静不说话，**连接撑过 3 分钟且无 `code=1005`** → 该消息算"业务活跃"；仍在 ~70s 被 1005 回收 → 排除。每候选跑 4–5 分钟。

**设备窗口估算**：4 个候选各 5 分钟 = 20 分钟；加切换/核对/回退 ≈ **25 分钟**（不含装机时间）。
切换候选后聊天页会立即重建连接（`wsProbeRevision` 监听），不必等 70s 自然回收，避免"候选有效→永远切不到下一个"的死锁。

### 5.1 406 帧构成（detect 连接 18:20:26→18:24:26）

| 类别 | 数量 | 说明 |
|---|---|---|
| 文本 JSON | 62 | `tts`=43、`stt`=8、`llm`=7、`mcp`=3、`hello`=1 |

### 5.2 三问逐一结论

1. **会不会触发服务端 ASR？——会。**
   每个 tick 后 <200ms 必回 `{"type":"stt","text":"小智"}`（8 tick = 8 条，文本完全一致）。
   证据：`18:20:56.536 发送 listen detect` → `18:20:56.648 收到 stt("小智")`。
2. **会不会推 TTS 给我们播？——会，且真实外放。**
   `stt` 后紧接 `tts start` → `llm("😊","happy")` → `tts sentence_start`（"哎，我在呢！""有什么事要我帮忙吗？"等，
   8 tick 各不相同）→ `tts stop`。窗口内 `AudioTrack(29296)` 共 **10 次 start**，
   `18:20:58.868 AudioTrack set() ... sampleRate 16000` 实证外放。43 条 tts 文本 / 344 个音频帧即由此产生。
3. **会不会让设备麦克风被打开？——未证实（本窗口内未见）。**
   全程 `AudioRecord*` 命中 **0 条**（pid 29296），App 未启动录音；但服务端在没有上行音频的情况下仍返回了
   `stt("小智")`，说明"识别"是服务端在 detect 模式下自行判定/回填，其内部机制**未证实**。

### 5.3 风险评估（上线前必读）

- `detect` 保活的本质是"**每 45s 主动叫醒一次助手**"：能续命，但会自言自语，且每次都真实占用 TTS/播放链路。
- 因此 **v6.11.9 起生产默认 `off`**，`detect` 仅保留为开发者诊断项；生产靠"WS ping + 无感重连"兜底。
- 若未来必须用 detect，必须满足：仅在空闲时发（`markConversationActive/Idle` + 5s 恢复）、间隔 ≥45s，
  并接受"每隔一段时间的问候语"这一产品代价。
- 待验证（下一设备窗口）：`detect` 是否会打断用户正在说的话（本次未测并发场景）；服务端 `stt("小智")` 的产生条件。

## 7. 无副作用候选 ⑤/⑥（v6.11.10+62，待设备窗口）

> 目标：找到"能续命"且"零副作用"的业务帧。判定必须**两个条件同时成立**：
> ① 安静 3 分钟无 `1005`；② 全程零 `stt`、零 `tts`、零下行二进制、零 `AudioTrack start`。
> 任一副作用命中 → 判"有效但有副作用"，与 detect 同罪，不得默认开启。

| 候选 | 每个 tick 的载荷 | 语义假设 | 风险点 |
|---|---|---|---|
| ⑤ `stop` | `{"type":"listen","state":"stop"}` | "停止监听"，服务端应忽略/回 ACK | 服务端可能对空闲 stop 回错误帧 |
| ⑥ `pair` | `{"type":"listen","state":"start","mode":"manual"}` + `{"type":"listen","state":"stop"}` | 成对进入/退出监听，不产生会话 | start 可能短暂开麦/触发 VAD |
| ⑥' `mcp` | `{"type":"mcp","payload":{"jsonrpc":"2.0","method":"notifications/initialized"}}` | MCP 通知不算会话，但算"业务活跃" | 未知 method 可能被服务端判非法并关闭 |

**判定流程（每候选 4 分钟，间隔 30s，共约 12 分钟）**
1. 开发者中心 →「WS 保活探针」切到候选（切换即重建连接）；
2. `adb -s 36c77fb6 logcat -s flutter | findstr "[PROBE]"` 存盘；
3. 判 ①：`[PROBE] 停止（服务器断开 code=1005）` 是否在 180s 内出现；
4. 判 ②：`[PROBE] 下行` 中是否出现 `type=stt|tts|llm`、`type=binary`；另查
   `AudioTrack(29296)` start 数（应为 0）；
5. 结论写入本文件 §7 表下方，并回填 README 版本档案。

辅助脚本：`tools/ws_probe_judge.ps1`（传入 logcat 文件与起始时间，输出两条件判定）。

## 8. 重连频率评估（70s 回收下的真实压力）

**理论值（空转 1 小时）**：3600 / 69.8 ≈ **51.5 次**重连/小时；每次重连 = 1 次 WS 握手 + 1 条 `hello`
（服务端侧等价于一次新会话）。一天约 **1,236 次**。这是"无感重连"方案的固有成本。

**评估方法（不需要改代码，日志已内置）**
- 采集：`adb -s 36c77fb6 logcat -s flutter | findstr "[RECONNECT]"`，连续 1 小时；
- 统计：`[RECONNECT] 汇总` 每 10 次自动打印 `累计/成功/失败/间隔(avg/min/max)/近20次 closeCode`；
- 判读：
  - `closeCode` 应全部为 `1005`（正常回收）；出现 `432x` = 身份问题，出现 `-1`（无码）= 网络层异常；
  - `失败` 持续 > 0 或 `间隔` 明显 < 60s → 服务端可能在限流/抖动；
  - 若 1 小时内出现任何 `429`/`too many`/`432`，视为"过频"。

**若判定过频，切换策略（备选，不默认启用）**
- "仅在需要时说前连"：空闲期主动 `disconnect()`，用户按下麦克风/说话时由 v6.11.10 的
  2s 预连接（`_ensureConnectedThen`）即时建连，连上再采音；把"每分钟 1 次"降到"每次使用 1 次"。
- 代价：首字延迟增加约 200–600ms（握手 + hello ACK），需用 `[PRECONNECT] 成功，xxx ms` 实测分布确认。

## 10. 技术结论链（v6.11.11 定案，公开 README 引用本段）

1. **现象**：安静不说话时，云端在 **60–70s** 内关闭 WS，关闭码 **1005**（无 close frame，静默回收）。
2. **ping 无效**：`pingInterval=25s` 实测仍 65–68s 被回收 —— 服务端按**业务消息**判活跃，不认 WS 层 ping。
3. **detect 能续命但有毒**：`listen{state:"detect"}` 每次 tick 触发 `stt→llm→tts`，
   8 tick = 406 帧（62 文本 + 344 音频）、10 次 `AudioTrack start`，会真实外放"自说自话"。
4. **stop 干净有效**：`listen{state:"stop"}` 每 45s 一次，8 tick / 6 分钟零副作用、零重连（§7.1 数据）。
5. **生产实现**：`keepalive=auto` 默认开启；只在"已连接且无会话"时发；对话中暂停、结束 5s 后恢复、
   60s 无活动兜底；与业务会话共用同一个"会话进行中"标记，避免两套状态打架。

## 11. 测试工具的伪影：一次差点误判为代码缺陷的 adb 往返

### 11.1 现象

v6.11.11 的真机 B 段（2026-11-04，D 窗口）里，从"该发消息了"到日志出现
`markConversationActive` 之间，**量到 4–5 秒**。当时的第一判断是：
"置位排在发送流程之后，被 await 阻塞了" —— 这是一个会导致保活帧插进用户说话的
真实缺陷，因此差点直接改代码。

实际是**测量方法**的问题：那 4–5 秒里绝大部分是我们自己串行调用 adb 的往返开销，
不是应用内耗时。

### 11.2 复算过程（按当时的 adb 命令序列逐步拆）

注入脚本（主机侧）写 `D_START` 后，依次执行三条 adb 命令，每条都要：
`adb.exe` 进程冷启动 → USB/ADB 传输 → 设备端 `input` 解析 → 注入触摸事件。

| 步骤 | 动作 | 主机时刻 | 说明 |
|---|---|---|---|
| 0 | 写 `D_START` | 20:21:41.0 | 计时起点，此时**还没有**任何触摸发生 |
| 1 | `adb shell input tap` 点输入框 | ≈20:21:42.2 | 命令往返 ≈1.0–1.3s |
| 2 | `Start-Sleep 500ms` + `input text` | ≈20:21:43.5 | 500ms 是我们自己加的等待 |
| 3 | `Start-Sleep 500ms` + `input tap` 点发送 | ≈20:21:44.8 | 又一次往返 ≈1.0–1.3s |
| 4 | 设备内：点击 → 置位 | 20:21:46.334 | 见 11.3，**≈1.0s** |

`20:21:46.334 - 20:21:41.0 ≈ 5.3s`，其中：

- **≈3.0–3.9s** 是三条 adb 命令的串行往返（工具开销）；
- **1.0s** 是脚本自己 `Start-Sleep 500ms × 2` 的等待；
- **≈1.0s** 才是"设备真的被点到 → 应用打日志"这一段（含 Flutter 帧调度与触摸事件派发）。

后两项之外的 3 秒多，用户根本没有"开口"，是我们自己在等 adb。

### 11.3 代码事实与实测反证

处置方式：读代码确认顺序，而不是照着误差改代码。

- 文字路径：`markConversationActive('发送文字')` 位于 `_sendTextMessage()` **第一条语句**，
  之前只有 `_liftVoiceMuteWindow()`（纯内存操作）和 `trim()`，**没有任何 await**。
- 语音路径：`_handleAudioStart()` 的置位在 `listen{state:"start"}` 上行之前
  （v6.11.12 真机实测：置位 20:53:23.284 → listen start 上行 20:53:23.285，早 1ms；
  首帧上行音频 20:53:23.806，晚 522ms）。

v6.11.12+64 实测埋点原样（设备时钟）：

```
20:49:36.794 [KEEPALIVE] 进入会话，保活暂停（发送文字）
20:49:36.794 [KEEPALIVE] 置位 来源=发送文字 耗时=0ms 顺序=发送前
20:49:36.798 发送消息: {"type":"listen","state":"detect","text":"...","source":"text"}
```

置位与上行只差 **2–4ms**，`耗时=0ms`（同一毫秒内完成）。
所谓 4–5s 在应用侧并不存在。

### 11.4 以后怎么避免重复踩

1. **计时起点必须贴近被测事件**：`D_START` 写在 adb 命令**之前**等于把工具开销算进应用；
   正确做法是让设备端在同一进程里打点（`logcat` 自带时间戳）。
2. **一条 adb 命令 ≈1s 起**（冷启动进程更贵）。需要连发多步 UI 操作时，
   串行 adb 的累计延迟会线性叠加，**不要用它测交互延迟**。
3. 要测用户可感知延迟，用 `uiautomator`/instrumentation 在设备内一次跑完，
   或直接引用应用自带埋点（本项目的 `耗时=Nms` 字段就是为此加的）。
4. 结论口径：**怀疑"代码慢"之前，先把测量链路的每一段延迟拆出来**。
   本次拆完发现"真凶"是 adb 往返，"嫌疑人"是清白的。

## 12. v6.11.14：中文边界实测，以及 `detect` 文本上限到底是什么口径

### 12.1 为什么要开一个 adb 中文注入通道

`adb shell input text` 只支持 ASCII，测不了"用户打中文"；`cmd clipboard set-text`
在本机返回 `No shell command implementation.`，剪贴板通道也不可用。
最终走 **Intent extra（UTF-8 原生支持）+ MethodChannel**，仅开发者模式生效：

```
# ① 原样单帧（绕过分段）——量服务端真实边界
adb -s 36c77fb6 shell am force-stop com.zcstudy.xiaole
adb -s 36c77fb6 shell am start -n com.zcstudy.xiaole/.MainActivity \
  -e debug_send_texts "中文一<换行>中文二"

# ② 走真实发送路径（分段/排队/兜底）——回归"长中文一定被切开且每段都有回复"
adb -s 36c77fb6 shell am start -n com.zcstudy.xiaole/.MainActivity \
  -e debug_send_text_seg "六十个字左右的中文……"
```

- 前提：**开发者模式已授权**（`AppFeats.devAuthed`，密码 `zc19901111`，解锁一次持久化）。
  未授权时通道完全不生效，release 普通用户路径不暴露任何入口。
- 日志前缀 `[DEBUGINJECT]`，一次打出 `码点 / utf8字节 / utf16` 三个口径，
  随后是 `发送文本请求: {...}` 与服务端 `stt` / `tts` / `alert`。
- 坑：`am start` 的 extra **含空格会被 adb shell 当参数分隔符**（实测
  `"the quick brown fox"` 到达应用只剩 `"the"`），带空格的用例必须整体加引号。

### 12.2 实测数据（2026-11-04，官方 api.xiaozhi.me 云端，真机 RMX3161）

被拒时固定返回
`{"type":"alert","emotion":"sad","status":"ERROR","message":"Detect is only for wake words, do not send long texts."}`，
且不产生任何 stt/llm/tts。

| 内容类别 | 通过 | 被拒 |
|---|---|---|
| 纯 ASCII 字母数字 | 31 / 32 / 33 / 34 / 40 | 60 |
| 纯汉字（无标点） | 11 / 16 | 17 / 18 / 19 / 20 / 25 / 30 / 33 / 34 / 40 |
| 汉字 + 标点 | 15 码点 / 16 码点 | 17 码点；16 汉字 + 2 标点（18 码点） |
| 真实中英混排（`帮我查下iPhone15多少钱` 15 码点、`帮我看下iPhone价格` 12 码点） | 通过 | — |
| 单字母交替式混排（`中A文B混C排D测E试F…`） | 12 码点 | 13 码点 |
| 纯 emoji（astral，单码点） | 8 / 9 / 10 个 | 11 / 16 / 33 / 34 个 |

### 12.3 结论：云端不是按单一字符数、也不是按单一字节数

三条同时成立的证据：

1. **48 字节通过，44 字节被拒**：16 个纯汉字 = 48 UTF-8 字节被收；
   11 个 emoji = 44 字节被拒 → 不是"UTF-8 字节 ≤33/48"这类单一阈值。
2. **同样 48 字节，码点不同结果不同**：16 汉字（16 码点）通过，
   `16 汉字 + 2 标点`（18 码点、48 字节）被拒 → 标点也占预算。
3. **ASCII 可以到 40 而 emoji 只到 10**，单字母交替混排 12 就到顶
   → 与"字符数"同样对不上。

表现最像**按内容类别加权的等效 token 预算**（CJK≈1/字、ASCII 词内可合并、
孤立字母与 emoji 更贵）。服务端闭源，无法拿到判据原文，因此**不猜公式，只取实测值**：

| 类别 | 实测通过上界 | 采用上限 | 余量 |
|---|---|---|---|
| 纯 ASCII | 40 | **33**（维持 v6.11.13） | 7 |
| 汉字 / 中英混排 | 16 / 15 | **12** | 3–4 |
| 含 astral（emoji） | 10 | **10** | 0（该类别已是最小实测值） |

切段函数 `_splitTextForDetect` 同时累加**码点**与**UTF-8 字节**（先到者为准），
上限集中在 `_textLimitsFor()` 的三个常量里；云端口径若变，只改数字，不用重写逻辑。
